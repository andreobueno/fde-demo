# Prototype assumptions vs production requirements

This prototype deliberately trades production concerns for speed and clarity. Each row states what the prototype does and what a production deployment handling real KYC data would need instead.

| Area | Prototype assumption | Production requirement |
| --- | --- | --- |
| Authentication / identity | Explicit local password adapter with public fictional credentials, salted scrypt hashes and server sessions (one hour idle, 12 hours absolute). The development-only picker loads retained credentials from anonymous `/api/auth/demo-users`, submits email/public password to sign-in, then installs `/api/me` identity. Anyone reaching the enabled adapter can use seeded manager credentials. IDs/role labels alone cannot authenticate. Local auth is rejected in production and demo sessions cannot authenticate when it is disabled; separately provisioned automation tokens still work. | SSO/OIDC (e.g. Entra ID, Okta), controlled provisioning from the IdP/HR directory, managed server sessions and MFA. |
| Browser sessions | Both SPAs keep only session tokens in JavaScript-readable, tab/origin-scoped `sessionStorage` and verify restored tokens through `/api/me`. Duplicated/opener-created tabs may inherit a token. SSR uses HttpOnly, SameSite=Strict, Secure-by-default cookies with configurable instance names; cookies are shared across tabs and are not port-scoped. Copies of a token share revocation/expiry; independent logins do not. | Reviewed BFF/HttpOnly cookie transport, CSRF/XSS defenses and session lifecycle controls. Cookie names and distinct local ports are demo conveniences, not security boundaries between untrusted applications sharing a host. |
| Authorization | Central server permission matrix for analyst, senior analyst and compliance manager. Mutation services reload stored actors. Case decisions use current risk/state; refund decisions also check amount. Analysts cannot decide; seniors decide low/medium cases and low/medium refunds up to USD 5,000; managers decide all supported risks/amounts and manage policy. All roles read all cases/refunds. | Controlled role provisioning, assignment/tenant/field-level scope, separation of duties (maker/checker), audited access grants and periodic access reviews. |
| Database | Single SQLite file (`packages/server/data/kyc.db` by default), WAL, foreign keys and recursive triggers. Startup applies schema plus idempotent role, refund-audit and document-expiry migrations; it does not reset business data. There is no versioned migration ledger. | Managed database with controlled/versioned migrations, connection pooling as needed, PITR backups tested by restore drills, per-environment credentials and a scaling plan. |
| Seeding | Full `seed` drops/recreates business data, policy/history and credentials. `seed:logins` replaces retained analysts' passwords and revokes browser sessions while preserving business/auth history and automation tokens. `seed:refunds` adds missing fictional refund IDs and retains decisions/history. Full/login seeds reject production; refund-only seeding has no `NODE_ENV` guard and relies on fictional customer conventions. | Keep demo commands away from production data and credentials; use controlled imports/provisioning and separately validated data migrations. |
| Audit immutability | Case and refund chains share `audit_events` but sequence/hash independently per subject. Approval-note policy has a separate hash chain; risk-policy and auth histories are append-only without hashes. Business mutations and their history writes are atomic. Triggers/recursive triggers reject update/delete/replace through the app's DB connection. No audit-edit API exists. Hashes live beside operational data; a DB administrator can bypass controls or remove a chain tail. | Separate append-only/WORM storage, restricted writer privileges, externally anchored chain heads, defined retention, monitored verification and restore tests. Include access/denial/admin events and decision-time role/policy evidence. |
| Review policy | Manager-only setting for low/medium approval notes, version conflict checks, mandatory change reason and before/after audit snapshots. High-risk role/note boundaries are fixed. | Dual approval/change control for sensitive policy updates, policy version retained on case decisions, staged rollout and periodic governance review. |
| Risk engine | Deterministic signal sum capped at 100. Predicates/defaults are code; weights/thresholds persist in `risk_policy`. Manager patches append independently versioned `risk_policy_changes` and rescore open cases atomically, recording changed evaluations and threshold snapshots. Closed cases retain their evaluation. Explanations use saved score/level/signals/thresholds, with default 30/60 fallback for missing snapshots. No complete per-case evaluation-version history or scheduled rescore exists. | Complete ruleset/evidence snapshots per decision, change control with dual approval, back-testing before rollout, model governance if ML is introduced, and retained regulator-readable rationale. Any LLM-written summary must cite the structured result and cannot become the policy source of truth. |
| Data | Fictional customer fixtures use a fixed-seed PRNG, with dates relative to seed time and random audit/signal IDs. No application-level encryption of SQLite data. | Real PII: encryption at rest and in transit, field-level encryption or tokenisation for identifiers, data minimisation, field-level access controls and masking in the UI, data residency constraints, GDPR rights (access/erasure balanced against AML retention obligations), documented retention and deletion schedule. |
| Secrets / config | API settings include `HOST`, `PORT`, `KYC_DB_PATH`, `LOCAL_DEMO_AUTH` and the production guard. SSR adds `API_URL`, `SESSION_COOKIE_NAME` and `ALLOW_INSECURE_LOCAL_AUTH`. Password/session/automation-token secrets are hashed in SQLite; identity metadata remains readable. The automation CLI requests a new file with mode `0600` and refuses overwrite; deployment filesystem permissions still matter. | Secrets manager (Vault, AWS Secrets Manager), secure credential delivery, no real secrets in repo or images, rotation, per-environment config validated at startup. |
| Observability | Startup console message, JSON API errors and database authentication events. Unexpected API errors return a generic `500`; the handler does not log their stacks. | Structured logs with request ids, metrics (latency, error rate, queue depth by status), tracing, alerting, log retention that excludes PII, dashboards for analyst throughput and SLA. |
| Rate limiting / CSRF / CSP | Security headers, `Cache-Control: no-store`, localhost/127.0.0.1 CORS allow-list, explicit bearer API headers. The selected SPA preserves same-origin proxy cookies; the API ignores cookies for identity. SSR form requests require an Origin matching the request host/expected protocol and reject `Sec-Fetch-Site: cross-site`; GET/HEAD/OPTIONS are exempt. In-process login throttles use email and socket IP; no general API rate limit. | Durable/distributed rate limiting and abuse detection, reviewed CSRF protection and trusted-host/proxy configuration for cookie auth, strict CSP, HSTS, tested body-limit/error handling, dependency and container scanning. |
| Deployment | Development-oriented `tsx` server scripts and SQLite on disk. API `dev` sets loopback host/local auth; ordinary `start` honors environment values and does not force loopback or enable local auth. `/api/health` returns a static `{ok: true}` rather than checking dependencies. | Containers built in CI, image signing, CD with staged environments, infrastructure as code, dependency-aware health/readiness probes, zero-downtime deploys and rollback procedure. |
| Testing | Vitest role/risk/state matrix, Supertest HTTP integration tests, password/session tests, transactional rollback/migration tests and web identity/note-rule tests. Repository scripts provide lint/typecheck/test commands; no CI workflow is tracked in this checkout. | Add repeatable end-to-end browser tests, load tests, security tests of real authentication and enforced CI gates. |
| Multi-user concurrency | Immediate SQLite transactions serialize case/refund/policy writes and recheck current state/permissions. Approval-note policy requires the client's current version. Cases/refunds and risk-policy patches have no client version; risk patches merge into current settings, with the last accepted write to each setting taking effect. | Optimistic locking (`If-Match`/version column) so a stale view cannot act, idempotency keys as needed, explicit case locking or assignment and UI refresh on conflict. |
| Case assignment / SLA | A shared review queue exists. Case actions set `assignedTo` to the actor, but assignment does not restrict reads or decisions. No claim/release or SLA deadlines. | Assignment rules (round-robin, workload, seniority), claim/release, SLA timers with breach alerts, escalation paths and supervisor dashboards. |
| Notifications | Local UI feedback/toasts; no external notifications or delivery service. | Email/Slack/in-app notifications for escalations, SLA breaches and reassignment; digest for seniors. |
| Document storage (ID scans) | Verification booleans and optional ID-document expiry metadata; no scan upload/storage. | Encrypted object storage with signed, expiring URLs, virus scanning, access logging, retention tied to the case, redaction tooling and integration with an IDV provider. |
| Integrations | Sanctions/PEP flags and an adverse-media hit count are seeded inputs; no live screening integration. | Screening providers with re-screening schedules, webhook ingestion and provider outage handling. |

## What this prototype demonstrates about the Power Apps replacement question

What this repository demonstrates:

- **Explicit, testable rules.** Case/refund transitions, role permissions and risk scoring have
  domain tests. Supertest exercises the API against in-memory SQLite; these are HTTP integration
  tests, not a deployed-browser test suite.
- **Reviewable source.** Rules, schema and UI are ordinary version-controlled files. Lint,
  typecheck and test scripts exist; the repository does not establish that every change receives
  a PR or CI run.
- **Shared architecture in use.** KYC and refunds share the selected UI shell, authentication,
  database, audit storage and reusable components inside one application. They have separate
  domain rules and services. There is no separately packaged internal-tool framework to copy.
- **Multiple clients.** The selected SPA and two reference implementations use the same HTTP
  API. A database replacement would still require repository SQL, schema and transaction changes;
  the pure rule functions are the clearest reusable boundary.

This code does not establish comparative development speed, testing capabilities or operating
costs for Power Apps. Evaluate those against the organization's actual platform configuration
and requirements. Compare identity/governance, available connectors, non-engineer editing,
testing/review workflow, licensing and operational ownership for each proposed tool.

The table above identifies work still required to handle real KYC data. Reusing this
application's modules can reduce duplication, but does not by itself supply those production
controls or justify migrating every internal app.
