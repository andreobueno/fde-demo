# Refund Operations API

Refund Operations uses the existing Express app, SQLite connection, customers, analysts,
permission model, service transactions and audit repository. It records review decisions only:
there is no payment execution, payout integration, new dependency or separate service.

All endpoints below require a known, database-resolved `x-analyst-id`. This is the existing
simulated demo identity mechanism, not production authentication.

## Types

```ts
type RefundStatus = 'pending' | 'approved' | 'rejected';
type RefundAction = 'approve' | 'reject';
type RiskLevel = 'low' | 'medium' | 'high';
type RefundSort = 'reference' | 'customer' | 'amountCents' | 'status' | 'riskLevel' | 'createdAt';
type RefundAmountBand = 'all' | 'under_1000' | '1000_to_5000' | 'over_5000';

interface Refund {
  id: string;
  reference: string;
  customerId: string;
  customer: { id: string; fullName: string; email: string };
  amountCents: number;
  currency: 'USD';
  status: RefundStatus;
  riskLevel: RiskLevel;
  reason: string;
  originalTransaction: { reference: string; amountCents: number; occurredAt: string };
  riskIndicators: Array<{ code: string; title: string; description: string; severity: RiskLevel }>;
  createdAt: string;
  updatedAt: string;
}

type RefundAuditEvent = Omit<AuditEvent, 'caseId'> & { refundId: string };
interface RefundDetail extends Refund {
  allowedActions: RefundAction[];
  approvalNoteRequired: true;
  audit: RefundAuditEvent[];
}
```

`AuditEvent` retains its existing ID, sequence, actor ID/name, action, previous/new status,
note, timestamp, previous hash and hash fields. Refund event statuses use only `pending`,
`approved`, `rejected` or `null`. Refund responses never label a refund ID as `caseId`.
Dates generated by this API and seed are UTC ISO 8601 strings.

Money is positive safe integer cents; refund amount cannot exceed original transaction
amount. USD is the only currency. Repository validation and SQLite constraints enforce
these invariants. There is no HTTP endpoint to create refunds or alter risk, amounts,
customer data or original transaction details.

## Routes

| Method / path | Result | Permissions |
| --- | --- | --- |
| `GET /api/refunds` | `{ items: Refund[], total, page, pageSize }` | `refunds:read` |
| `GET /api/refunds/stats` | `{ pendingCount, pendingAmountCents, approvedToday, rejectedToday }` | `refunds:read` |
| `GET /api/refunds/:id` | `RefundDetail` | `refunds:read` and `audit:read` |
| `GET /api/refunds/:id/audit` | `RefundAuditEvent[]` in ascending sequence | `refunds:read` and `audit:read` |
| `POST /api/refunds/:id/actions` | `RefundDetail` | Read/audit permissions plus decision rules below |

The action body is exactly `{ "action": "approve" | "reject", "note": "..." }`.
Both actions require a trimmed note of 10–1000 characters. Unknown fields are rejected,
including actor, role, status, amount and risk fields. KYC's configurable approval-note
policy does not apply to refunds.

List query:

| Parameter | Default | Accepted values |
| --- | --- | --- |
| `q` | absent | Trimmed text, max 100 characters; literal substring match against reference, customer name/email, original transaction reference |
| `status` | all | Comma-separated refund statuses |
| `riskLevel` | all | Comma-separated `low,medium,high` |
| `amountBand` | `all` | `all`, `under_1000`, `1000_to_5000`, `over_5000` |
| `sort` | `createdAt` | `RefundSort` |
| `order` | `desc` | `asc`, `desc` |
| `page` | `1` | Positive integer with a safe SQLite pagination offset |
| `pageSize` | `25` | Integer 1–100 |

Amount bands: `<100000`, inclusive `100000..500000`, and `>500000` cents respectively.
Risk sorting follows low → medium → high; customer sorting is case insensitive.
Every sort breaks ties by ascending refund ID. Unknown query keys and invalid enums
return 400. Values are bound parameters; sort expressions come from an enum whitelist.

Stats ignore list filters. Pending totals cover all pending refunds. Today is the current
UTC calendar day, `[00:00:00.000Z, next midnight)`, based on decision audit timestamps,
not request creation or row update dates. Approvals/rejections count distinct refund IDs
with the corresponding action and pending-to-terminal transition.

### Known aggregate-money limit

`pendingAmountCents` is a JSON number populated from SQLite's integer `SUM`. Exact
cent precision is supported only while the pending total stays within
`Number.MAX_SAFE_INTEGER`: 9,007,199,254,740,991 cents ($90,071,992,547,409.91).
The prototype does **not** enforce this aggregate bound; validating each refund as
a safe integer does not ensure that their sum is safe.

Above that bound, conversion to a JavaScript number can lose cents. If the sum exceeds
SQLite's signed 64-bit integer maximum (9,223,372,036,854,775,807 cents), `SUM` raises
an overflow error and `GET /api/refunds/stats` returns 500 `INTERNAL`.

This is an accepted prototype limitation; the seeded totals stay well below it.
The API remains numeric, with no new aggregate validation or arbitrary-precision
accumulation. Before production, choose an exact aggregate representation or enforce
an aggregate bound consistent with the chosen representation.

## Authorization and transitions

All roles retain every KYC permission and receive `refunds:read`.

| Role | Refund decisions |
| --- | --- |
| `analyst` | None |
| `senior_analyst` | `refunds:decide_low_medium`: low/medium risk **and** amount ≤500000 cents |
| `compliance_manager` | Both decision permissions; any refund risk or amount |

Only pending → approved/rejected is legal. There is no reopening or further action.
`allowedActions` and mutation authorization share the same pure transition validator.
The service re-reads the saved analyst role and saved refund state/risk/amount inside
an immediate SQLite transaction. The state update and shared audit append commit or
roll back together. A second decision returns 409 without another event.

Errors use the existing `{ error: { code, message, details? } }` envelope:
401 `UNAUTHORIZED` for missing/unknown identity, 400 `VALIDATION_ERROR` for invalid
input, 403 `FORBIDDEN` for missing permission, 404 `NOT_FOUND`, and 409
`INVALID_TRANSITION` for terminal refunds. Internal failures return 500 `INTERNAL`.

## Shared audit storage and canonical hashing

The existing `audit_events` table now contains nullable `case_id` and `refund_id` foreign
keys with a CHECK requiring exactly one subject, and separate unique subject/sequence
constraints. Existing KYC columns, contents and hashes are copied verbatim; the only
new value on old rows is `refund_id = NULL`. Case and refund IDs may have the same text
without sharing audit events or sequence numbers.

Refund canonical JSON has this exact key order:

```ts
JSON.stringify({
  action, actorId, refundId, createdAt, fromStatus, note, sequence, toStatus
})
```

`hash = sha256(prevHash + canonicalJson)`. Genesis uses 64 zeroes as `prevHash`.
KYC canonicalization keeps its legacy `caseId` key and ordering unchanged.
Both subjects use `computeEventHash`, `verifyChain`, and `insertAuditEvent`.

UPDATE/DELETE triggers and enabled recursive triggers block replacements, including
`INSERT OR REPLACE`. No role has an API to mutate history or insert arbitrary audit
events. As with the existing KYC chain, actor display names are not hashed; a database
administrator can rewrite a complete chain or truncate its tail. External immutable
storage/anchoring and authenticated identity remain production work.

## Migration and seeding

Startup creates refunds before migrating the old case-only audit table within an
immediate transaction. It copies existing fields without recomputing hashes, reinstates
append-only triggers, then creates the refund audit index and verifies foreign keys.
Startup is idempotent. Back up retained databases before schema upgrades. No KYC reset
is needed to migrate or add refunds.

`npm run seed` remains the existing **destructive fictional demo reset**, now followed
by `seedRefunds(db, now)`. `npm run seed:refunds` is additive and retains existing refunds,
decisions and history. It uses stable `refund-001`…`refund-018` IDs and reuses customers
matching the existing demo customer-ID and fictional-email conventions. These conventions
identify demo fixtures, not a guarantee that an arbitrary database contains no real data.
Run only against a known fictional demo database. With no matching seeded customers or
eligible analysts it fails with guidance instead of inventing customer or analyst records.

Fresh fixtures include 12 pending requests spanning every risk level and 99999, 100000,
500000, 500001-cent boundaries, plus six terminal requests across today and prior days.
Risk indicators are recorded deterministic fictional evidence, not live fraud detection.
Each request receives a hashed `REFUND_CREATED` genesis event; terminal fixtures receive
a truthful subsequent approval/rejection with an authorized existing analyst and note.
An additive rerun skips existing IDs entirely, so it never resets decisions or refreshes
old decision timestamps into today's stats.
